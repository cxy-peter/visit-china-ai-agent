# Visit China AI：项目复盘与决策记录

整理日期：2026-09-25。当前产品口径为 V6.4，PR #1 已于当日合并至 `main`，合并提交为 `0a1556ff8ad65e79370b2618c0fb3a8ad8354de5`，其文件内容与已验收应用提交 `0c321e758a270ee10ec6966cff04a249bc23c0f5` 一致。本稿依据本轮需求、代码和验收记录，重建问题、选择、结果与反思；“心路历程”写成有依据的项目判断，不替项目负责人虚构情绪或商业成绩。

## 1. 这个项目究竟在解决什么

Visit China AI 是面向入境旅行场景的个人产品原型，重点是上海，并保留北京及全国适用的资料索引。它希望解决的不是“游客能否和模型聊天”，而是游客在具体地点、具体限制下，能否得到有出处、能继续行动的回答。

典型问题包括：刚到浦东机场，怎样前往虹桥火车站；上海站周围哪里查询充电宝；银行卡能否用于某种购票渠道；一天怎样安排某个区的景点；比较高铁席别、历史价格与出发时间。问题通常同时带有地点、服务、条件和上下文，单纯匹配“火车站”“银行卡”等词会出错。

项目的第二个使用者是运营。运营需要知道一次回答为什么没解决：是听错、理解错、资料没找到、资料过时、流程走错，还是服务连接失败。只有能定位原因、提出改动、回放评测并决定发布，反馈才有改进价值。

因此，产品有两条相连的路径：旅行者提出问题并得到回答；运营根据证据和反馈改善系统。Source Library 是两者共用的知识基础。

## 2. 需求如何逐步收敛

下表是功能演进顺序，不代表持续数月开发，也不代表每一阶段都已验证商业效果。

| 阶段 | 体验中暴露的问题 | 形成的方向 |
|---|---|---|
| 早期通话与行动卡 | 对话、点选、需求确认容易各走各的 | 共用会话状态、保留上下文、版本隔离和发布治理 |
| V5.2—V5.4 | 语音成本、转写不完整、说完看不到记录 | 探索不同语音方案；扩大对话区、显示双方消息、重置与新聊天 |
| V5.5—V5.6 | 旅行助手和资料库割裂，连接状态不透明 | 共用资料和模型入口，服务端接入 DeepSeek |
| V5.7—V5.9 | 地铁被识别成火车，资料有了却没有解决问题 | 站点工具、真实地点、解决反馈、运营看板与来源审核 |
| V6—V6.1 | 手工把资料代入对话；反馈无法定位原问题 | 自动 RAG、检索技能、上下文工单、体验码与回放 |
| V6.2—V6.3 | 语音被切断或收录自身播报，多需求互相覆盖 | 更耐心的收音、播报防回声、补充队列、分项回答、上海16区路线 |
| V6.4 | 场所名触发错误任务，反馈重复，推荐与问题不相关 | 服务与地点分离、统一反馈、20个开场问题、相关产品与官方活动 |
| V6.4 正式站复验 | 数字校验拦下机场指引；中文城市名导致资料过滤 | 有限数字修正、城市名规范化、保留失败与复验记录 |

这条演进路径说明：新增功能不是唯一进展。删去不稳定入口、减少重复反馈、保留用户明确给出的地点，也能明显改善任务完成体验。

## 3. 七个可以讲清楚的关键案例

### 案例一：问充电宝，为什么出现火车行程

用户问“上海火车站周围有充电宝吗”，真正的目标是查询充电服务，“上海火车站”只是地点。旧流程容易把地点里的“火车”识别为购票需求，继而显示铁路行程。

改进分两层：让 DeepSeek 根据请求动作识别服务；应用层再避免站名本身创建铁路任务。相关服务卡和产品入口也必须服从本轮意图。如果用户另外说“再从这里去杭州”，才保留第二个独立铁路任务。

验收既看模型返回的意图，也看界面是否仍然错误弹卡。后台分类正确，并不保证前端旧状态已经清理。这是为什么要同时做接口和真实浏览器验收。

### 案例二：查到了 JCB 资料，为什么仍回答“无法确认”

这里的关键不是再增加一个 JCB 关键词，而是区分四种信息：公开服务能力、用户个人条件、明确禁止条件，以及证据缺口。用户没有提供余额或免密设置，不能反推出某个卡组织不受支持。

相同规则适用于 AMEX、SIM、行李、无障碍和证件要求。铁路购票、第三方购票付款、地铁闸机刷卡、钱包绑卡也不是同一场景。检索到了相似内容，仍然需要核对适用渠道。

这形成了通用回答约束：先说资料明确支持什么，再说明适用条件；有明确反证才能说不支持。来源没写到，不等于禁止。

### 案例三：API Key 有了，为什么管理员仍连不上

“服务端拥有模型密钥”“访客获得本站访问权限”“实际模型调用成功”是三件事。此前把 DeepSeek API Key 放进本站体验码框，会得到访问码错误，用户很容易理解成 DeepSeek 没接好。

现在区分服务端 API Key、本站体验码和管理员会话；错误提示也区分输入类型、过期、撤销、次数用尽及上游错误。验收必须实际完成一轮模型回答，不能看到 `configured: true` 就宣布接入成功。

### 案例四：更自然的语音，为什么反而收录了自己的播报

希望随时开口打断是合理需求，但浏览器语音识别与系统播报同时运行，可能把扬声器内容再次识别成用户输入，产生错误循环。当前选择先保证稳定：只保留浏览器在线语音，播报时暂停识别，结束后自动续听，支持点按打断。

与此同时，保留较长停顿窗口、未结束句子的续说和草稿恢复；模型查询期间的补充先排队，在当前查询后合并处理。新聊天、挂断和过时请求不能覆盖新状态。

这是一项明确取舍：目前没有完成可靠的自动语音打断，也不等于豆包式全双工。不要用“更智能”掩盖技术边界。

### 案例五：明确起终点后，为什么还被要求选路线

“刚从浦东机场落地，去虹桥火车站怎么走、注意什么”是在要到达指引，不一定要求地铁换乘图。系统现在区分回答形式：到达指引用正文，明确地铁问题用站点图，席别和时段比较用表格，付款资格用服务说明。

资料负责支撑交通事实；模型可以组织取行李、看标识、核对车票等建议。终点已明确，就不再要求用户重新选择。地图仍是可用工具，但不应占据每一种回答。

### 案例六：有资料却不能回答，根因竟是城市名

正式站复验中，模型返回城市“上海”，资料库使用键值“Shanghai”。资料已被检索到，却在适用范围过滤时被误当作不同城市，最后返回“没有适用正文”。

修正放在意图结构的入口：统一上海、北京、中国的常见中英文写法，保留原始车站端点与未识别城市。这样可以同时改善多个服务类别，而不是给某一句机场问题写固定答案。

这一案例最值得保留的判断是：看起来像模型不聪明的问题，也可能来自数据格式或应用规则。应先查实际执行记录，再决定是否更换模型或增加向量数据库。

### 案例七：防止编造的校验，为什么也会损害体验

机场指引曾因数字没有出处而整段被拦下。直接放宽限制会增加风险；只让用户重试又没有完成任务。

改进是在生成时提供按来源区分的数字清单，禁止凭空补充费用和建议缓冲时间。如果生成仍未通过数字校验，允许一次针对性修正，再完整验证；反复编造仍拦截。多需求中某一项失败，其他已完成结果继续显示。

这里的数字检查是可追溯的防线，不是完整语义事实验证：同一个数字出现在资料里，仍不保证模型把它用在正确对象上。重要问题仍需人工抽检与原文核对。

## 4. 设计判断如何变化

项目最初容易把“能力更多”当作进展：更多语音模式、更多服务卡、更多资料、更多框架。实际体验逐渐把标准收敛到三个问题：这一轮有没有回答用户；资料是否真的适用；失败后能否定位并修正。

因此，当前保留轻量 RAG、站点关系图和固定执行流程，不因为出现 Graph、Harness 或 Agent 的概念就增加服务。知识库扩充有价值，但城市字段不一致、地点与任务混淆，必须先修应用链路。运营看板也不追求把所有指标填满，而是展示分母、样本、窗口和未接入状态。

“四种知道”可以作为工作方法：已知且有证据的进入回答；已知缺口明确记录并补资料；用户说不清的偏好通过选项澄清；尚未发现的问题通过未解决反馈、异常和新样本持续发现。它不意味着模型能够知道全部未知。

## 5. 已取得的结果，以及不能推出的结论

| 记录 | 当前结果 | 解释边界 |
|---|---:|---|
| 官方索引 | 5,000个去重URL | 不是5,000篇已核验现行正文 |
| 新增问法 | 5,000条，50主题 | 合成改写；其中17主题参考4篇社区讨论，不是5,000位用户 |
| 新问法目标资料召回 | 4,485/5,000，89.7% | 仍有515条未命中；不是答案正确率 |
| 新一轮 Loop | 12,000条 | 基线11,482，候选11,657；改善175，退化0，保留343条未命中 |
| Loop 变化 | 95.68% → 97.14% | 目标召回增加约1.46个百分点，不是线上解决率提升 |
| 程序与接口 | 372项通过 | 工程契约检查，不是372名用户 |
| 浏览器回归 | 221项通过 | 含受控模型和模拟语音，不能证明真人麦克风质量 |
| 正式站实测 | 27项检查、4组真实模型问题 | 覆盖关键流程，不足以估计整体准确率 |

旧20,000条回归、新5,000条检索问题和新12,000条Loop使用的标签、统计口径不同，不应直接相加成独立用户量，也不能用各自通过率作简单横向比较。Loop 产生的是候选，尚未自动激活，更没有训练 DeepSeek 权重。

## 6. 个人贡献应怎样表述

适合的定位是：个人产品项目，主导需求、交互、知识和运营闭环设计，借助 AI 完成大量工程实现、测试和交付。可以讲自己如何提出真实反馈、决定优先级、要求验收和守住边界。

不应把 AI 完成的代码说成全部亲手编写，不应把已有开源方案说成原创算法，也不应把演示账号规则说成真实五人运营团队。实习参考材料用于启发通用流程，不等于在公司上线了本项目。

最有说服力的个人判断，不是能背出多少框架名，而是能解释：为什么充电问题不该推荐火车；为什么没写个人额度不代表不支持；为什么查到正确文档仍可能答错；为什么有测试通过还要做正式站复验。

## 7. 下一步的合理优先级

以下是建议，尚未宣称实施：先建立新的人工标注真实问法集，单独测意图、召回、回答和完整任务；再改善回答时延、移动端真人语音与反馈率；有真实场景价值后再接供应商库存、订单回传和更多城市。

若引入向量检索，应在相同来源、相同封存样本与相同预算下比较召回、错误引用、耗时和成本，而不是以“安装了Milvus”作为验收。若要全双工语音，应专门验证回声抑制、双讲、网络抖动和误打断率。
