# Visit China AI V6.5｜技术实现与运营闭环

版本日期：2026-09-25。基于已合并 V6.4 `23872e9` 的增量更新。个人产品项目，产品与运营设计、AI辅助实现；不是OTA、机场或政府正式系统。

## 1. 本轮交付边界

V6.5补齐的是应用层的知识与回答链路：五城识别与适用范围、标准KB直出、保留原问的有限多查询、候选资格检查和运营可观测性。没有训练或微调DeepSeek权重，也不需要增加付费语音／Embedding／重排供应商。继续使用现有DeepSeek服务端适配。

项目统一名为Visit China AI。北京、上海、广州、深圳、香港共用会话和资料结构，但覆盖深度不同：上海保留原有静态地铁、地点及路线工具；北京有既有资料指引；广州、深圳、香港本轮补充精选官方／运营方入门资料及标准问答。没有声称五城均有同等商户、实时路线或履约能力。

V6.4的5,000个官方URL仍是原有索引规模。本轮另外增加5条精选来源摘要和5个双语标准答案条目，不能把它们叫5,005篇逐一核实的现行全文。原有1,114条正文抓取元数据和3,886条链接发现的性质不变。

## 2. 用户与运营两条路径

用户通过文字、语音转写或按钮提供需求。应用保留已知事实、修订号和上下文，模型只解释当前请求，不执行订单。对话里的多个任务各自回答；一项失败不应吞掉已经完成的其他结果。

运营从未解决反馈进入排查：查看用户自愿分享的脱敏上下文、实际使用的来源版本、意图与工具、KB／检索路径和返回检查。再选择补资料、改配置、回放或工程修复。关闭排查工单不改写用户原来的“未解决”评价。

执行流程：

```text
语音转写 / 文字 / 点选 → 共享会话状态
  ├─ 已登记的标准问题 → 当前来源 / 城市 / 版本检查 → 原标准答案
  └─ 非标准问题 → 有效内容初次召回 → DeepSeek结构化意图
       → 受限改写检查 / 有限正文读取 / 二次多查询
       → 工具或有据生成 → 来源与数字检查 → 候选资格检查
       → 展示、解决反馈与可选排查工单
运营 → 归因 → 资料或技能候选 → 验收 / 回放 → 人工发布 / 回滚
```

该流程是应用执行结构，不是模型内部思考链。当前没有部署LangGraph、Milvus或Neo4j；不要因为仓库保留旧探索文件就宣称相关服务在线。

## 4. 五城支持与香港范围隔离

城市键统一为Beijing、Shanghai、Guangzhou、Shenzhen和Hong Kong，同时处理常见简繁中文、英文别名和机场标识。未知城市继续保留，不替换成上海。机场代码CAN不按普通英文单词can识别。

`city-scope.applies`统一用于资料筛选、RAG片段和候选资格。城市明确不匹配时排除；资料标为China或缺少城市，并不能证明适用于香港。香港优先要求明确Hong Kong、hong-kong辖区或显式`appliesTo`。跨境资料需要列明适用城市，不依靠“全国通用”猜测。

“具有五城入口”不等于任意跨城线路规划。现有上海地铁图只在上海使用；香港的默认铁路平台入口指向港铁，不直接套用内地12306路径。已知自驾资格、支付门槛或票种等仍需相应来源，不从另一个城市复制。

| 城市 | 本轮精选内容 | 必须保留的限制 |
|---|---|---|
| 上海 | 浦东／虹桥国际到达服务中心 | 来源介绍，不保证当前柜台、库存和排队情况 |
| 北京 | 大兴机场工作人员协助的语言服务 | 不扩大为北京全部机场通用承诺 |
| 广州 | 白云T2国际服务中心 | 精选入门指引，无全市实时地点服务 |
| 深圳 | 宝安T3国际服务中心 | 依据有日期的介绍，现场需再次确认 |
| 香港 | 线上机场快线二维码票使用路径 | 与游客全日通、内地地铁票及购票渠道分开 |

## 5. 标准KB：如何避免每次都调用模型

### 5.1 注册与匹配

`kb-entries.json`当前有5个条目，各含中英文问题变体，共10个精确变体。字段包括条目ID、城市、问题变体、来源ID、预期来源SHA-256、条目版本及批准状态。

匹配只统一大小写、Unicode兼容形态、空白和少量标点，不做模糊语义匹配。一个问题额外加入签证、退款等条件后，不会只因前半句相同而直出；歧义条目同样退出。未命中返回明确原因，继续原有流程，而不是给出近似但不适用的标准答案。

### 5.2 版本与来源检查

直出前确认：条目已批准；关联来源存在、启用且处于复核期；城市与适用范围一致；完整来源指纹符合批准时快照。指纹绑定URL、城市、辖区、渠道、双语摘要、内容、发布日期、复核日期和publicationHash。

编辑、停用、过期、来源变化或重新发布都会使旧快路径失效。不能仅把复核日期向后改就继续使用旧批准。新增问题变体或新答案应重新核对原文、更新条目指纹、补测试，通过代码评审发布。当前不是开放给模型自动写入的无限FAQ。

### 5.3 接口与计费

`POST /api/chat`的`action=kb`以及本机`POST /api/v5/kb`提供只读标准查询。只返回已登记的公开摘要，不调用模型，也不访问任意URL；未配置DeepSeek Key或体验码仍可使用。云端有独立的单进程频率限制，不把它说成分布式防刷或付费额度。

一般问题的`action=answer`仍需要原有身份、模型配置、同意和额度检查。公开KB入口不能扩大为匿名任意生成接口。来源更新读取运营目录，因此线上停用后不能继续从旧浏览器缓存直出。

界面显示“标准KB答案·本轮零模型调用”，并能打开来源。0模型调用／0Token只针对该次标准回答，不等于整个站点免成本，也不推导已节省的人民币金额。单文件HTML没有服务端；公开KB路径应在本机服务或已部署Vercel接口上体验。

## 6. RAG与有限查询改写

### 6.1 现有检索基线

默认约520字符切片、60字符重叠、topK=8、词项覆盖阈值0.06。英文词项和中文二字片段进入BM25与稀疏TF-IDF余弦，再以RRF融合，结合标题命中、资料类型和覆盖率做确定性重排。同一父文档最多两个片段，避免一篇长文占满上下文。

稀疏TF-IDF不是学习型Embedding，规则重排也不是神经Cross-Encoder。标题、主题与正文的处理不是已经实现BM25F。来源停用、时效和城市属于准入条件，不能被更高相似度抵消。

### 6.2 原问、改写与融合

沿用DeepSeek原有的单条`retrieval_query`，不为改写另开一次模型请求。`retrieval-plan`保留原问，并检查候选提示词是否更换城市、渠道／卡组织、数字，或者删除否定。已知当前城市可以作为后续问句的上下文；不能替换问题里明确写出的另一城市。

原问始终是第一条查询；获准提示以“原问＋提示”形式补充，避免完全替换。模块最多接收两个提示，实际当前生成接口通常只提供一个。各查询共用一次编译的有效资料快照，以加权RRF融合，再执行父文档去重和topK限制。拒绝的提示保留原因，不悄悄生效。

检查是保守的词法约束，不保证识别所有复杂否定、渠道或跨语言语义。如果大量合法改写被拒绝，应该以新标注集评估后扩展，而不是直接关闭约束。现有模型自评不是正确标签。

### 6.3 性能与证据

批量评测使用固定输入快照；在线重新读取当前资料，防止来源停用后命中陈旧编译缓存。当前没有新增跨请求答案缓存。正式引入缓存时，必须把来源版本、城市、语言、问题变体和流程版本纳入键值，并验证撤销。

本轮没有进行同预算的学习型检索对照，不报告Embedding收益或模型准确率提升。历史2万条主要保护旧工具／资料边界，新模块的单元和接口用例另外列出，不能用历史通过率代替新多查询的真实语义评估。

## 7. 候选资格先于答案排序

`answer-guard`在最终工具／模型答案比较阶段检查来源存在、当前状态和城市／辖区。请求明确写出12306或MTR等已建模渠道、来源也有渠道元数据时，检查渠道是否相容。没有渠道元数据不等于完成了渠道事实验证。

无引用的纯偏好交流可以保留conversation-only身份，但不能被当成事实来源通过。涉及来源、数字与输出结构的原有验证继续执行。

通过资格检查后，才沿用直接回答、端点、行动性和长度等展示评分。V6.5不再直接拼接未经冲突核验的两份候选；即使看不出明显矛盾，也保守选择一份并记录未合并原因。重复文本与明显支持／不支持冲突有单独标记。

这不是完整语义事实裁判。数字出现在资料中，并不保证用于正确对象；同一来源被引用，也不能保证结论正确。既有有据数字清单和最多一次修正保留，复杂渠道／资格问题仍需人工抽检。路线工具的早返回仍走其原有来源与范围门禁，并非所有分支都调用同一个新择优函数。

## 8. 运营指标与可观察性

轨迹新增标准KB条目／来源指纹、零模型调用、改写获准／拒绝原因、查询数量及候选资格结果。标准轨迹不增加完整原始聊天或录音。公开KB命中后，云端可保存有限执行元数据；存储失败明确标记，不能假装持久化成功。

| 指标 | 分子／分母 | 不能推出什么 |
|---|---|---|
| 标准KB直出占比 | KB直出执行／同窗口已留存执行 | 不是全站独立用户比例，也不表示实际节约金额 |
| 检索有结果率 | 有片段执行／实际进入检索的留存执行 | KB直出不计为检索空结果；非空不是正确 |
| 用户确认解决率 | 已解决评价／有评价回答 | 未评价结果未知，不能直接推广到所有旅客 |
| 反馈覆盖率 | 关联到展示的评价／展示回答 | 覆盖率低时需解释选择偏差 |
| 完整回答耗时 | 已留存服务端totalMs分布 | 不是首字延迟或真实语音端到端延迟 |
| 相关平台外跳 | 匹配曝光后点击／曝光 | 不是订单、GMV或佣金 |

沿用30天和留存数量上限；大表中未接回传的转人工、订单等保持缺失。需要用实际身份和独立标注才能补充真人服务、模型正确和留存指标。

## 9. 人在回路与发布治理

行为工作流仍保留五个不同授权账号对同一候选哈希的审批、作者不能自批、重复投票不重复计数、改稿清票和旧会话固定版本。它不代表已经有五位自然人参与运营。

有界检索技能和资料有各自的管理员审核／发布机制，不全部走五票。标准KB初始条目采用来源受控的代码评审；当前没有新增可视化FAQ编审器或自动从用户反馈学习并发布答案。运营可以发现缺口，但要显式修改、验证和批准。

Loop的评测指纹增加城市、KB、多查询与候选校验相关实现。旧候选不能凭V6.4结论覆盖新的资料或执行逻辑。本轮不自动激活历史12,000条实验候选。模型权重没有改变。

需要的新一轮运营闭环：原问题与结果 → 阶段归因 → 最小修改 → 原例和边界复验 → 当前源码／知识／配置指纹 → 人工发布 → 观察与回滚。不能把“工单关闭”改写成原用户已经满意。

## 10. 语音、库存与隐私边界

保留浏览器在线语音的自动轮流播报／收听、点按打断、草稿和补充队列。没有新增真实全双工服务，不把模拟语音或文本测试叫麦克风准确率。机票、住宿、寄存与充电入口仍没有实时库存、付款和履约回执。

公网和本机使用不同部署入口；服务端Key、网站体验码、管理员会话是三种凭据。`.env`、运行数据库、Cookie、真实旅客对话、公司OCR和任何DCG资料不进入公开代码与文档。

本轮公开KB只允许登记的短问题查询，以公开来源摘要回答；它不能读取私人订单或公司知识。私人实习复盘和简历在单独交付包中，不放入此仓库。

## 11. 验收、失败记录与复现

新增 `v5/v65.test.js`覆盖五城／未知城市、香港范围、双语精确命中、编辑／过期／停用／重新发布失效、追加需求不误直出、改写约束、候选资格、指标分母和实际HTTP接口。

`v65_browser_test.py`验证五城按钮、无Key标准回答、来源入口、城市状态、Operations指标与轨迹；`v65_compat_browser_test.py`保留V6.4关键浏览器场景。浏览器使用可控模型fixture，不消耗付费模型，也不验证真人麦克风。

运行命令：

```bash
npm ci
npm test
npm run build
node tools/run-corpus-evaluation.cjs --output evidence/v6.5/historical-regression.json
python v5/v65_browser_test.py
python v5/v65_compat_browser_test.py
```

以 `evidence/v6.5/acceptance.json` 和CI实际记录为本轮结果。首次回归发现旧city-sh按钮ID被改动影响审批回放、新脚本未列入本机静态白名单、纯偏好回答被资格检查误拦；已分别保持旧ID、补资源名单和区分非事实对话。另一个测试发现新KB预算初始化不应消耗付费通路的注入时钟，已使其懒初始化。没有删除这些旧测试来换取通过。

工作容器的受管理Chromium禁止访问localhost，所以本机未取得浏览器交互成绩；浏览器结果应由CI独立运行后记录。早期仅因缺少锁定运行依赖而失败的本地检查，不能解释为模型效果问题；随后从锁定依赖重跑。

历史V6.4已有真实DeepSeek验收，但它不是V6.5实测。本轮没有真实Key，未发起新的付费模型调用；仍需小规模真人问法、语音噪声与线上端到端独立验收。

## 13. 简历和面试的准确定位

可表述：从实际反馈出发，多轮迭代Visit China AI，明确五城覆盖层级、知识直出和生成分工，完成低成本KB路径、约束保留检索、候选校验、运营回放和开发验收。

不可表述：五城全量服务已上线、零幻觉、真实转化提升、已降低客服人力、已经微调DeepSeek、三个独立模型并行择优或真人全双工成熟。模型代码由AI辅助实现，项目负责人的关键贡献是需求、交互、错误定位、优先级和验收判断。

“RAG前期是否需要微调”的回答：需要调优，但不必先训练权重。本轮改的是标准答案、查询、范围、检索配置和返回逻辑。数据与流程未稳定时，更换模型不能直接修复错误城市键或无效来源。后续是否增加Embedding／神经重排，应在同一批封存人工标注数据、预算与时延约束下比较。
